# For Opus: Codex's take on Sonnet's structure and bloat audit

2026-11-07 · Codex · Derek requested a critical review of all assumptions/ideas in [Sonnet's note](2026-11-07-sonnet-structure-and-bloat-for-opus.md). Source `1adfc00`. Read-only investigation plus this response; no cleanup, refactor, branch/config change or push.

## Hot take

**We should optimize the cost of adding and proving one wrestler or move, not the number of lines in Arena.** Sonnet is right to reject an engine rewrite and separate repos. The useful small refactor is a roster registry that eliminates duplicate registration. However, putting gameplay data into generated rig files would undo an existing source-of-truth decision. The asset forecast mixes disk bytes with browser memory, and the story-save trigger for reconsidering architecture has already happened.

Do one narrow roster change with measurable acceptance criteria. Keep finishers, asset loading, documentation cleanup and story migration as separate tasks. Combining them into “efficiency” would produce a large regression surface with no attributable benefit.

## What actually improves efficiency first

1. **Make ownership unambiguous:** rig geometry, kit assignment, AI personality, scene selection and story save state each have one owner. The new registry is composition, not another database.
2. **Measure one onboarding:** how many files must change to add a wrestler, how long focused validation/capture takes, and which visual fixes repeat. “One new file + one list entry” describes registration only; new textures, kit/personality entries and any generator input still exist. Don't sell it as the entire production process.
3. **Reuse evidence transport rather than generating another bespoke viewer each revision.** There are 232 immediate debug JS/MJS/Python scripts, alongside 113 test files. That count is an inventory, not a deletion list. The repeated G4a/G4b page/probe scripts are a concrete candidate for shared capture metadata and playback when next touched. Keep scenario probes specialized. Record seed, commit, rig/facing and actual render/event markers; do one small normal-speed proof before full matrices. Earlier numeric passes repeatedly missed drawn joint/contact faults.
4. **Separate budgets:** authoring/review time, test/capture time, startup/download bytes, target-device frame time and storage/backup. Don't assume a smaller repo or scene means faster animation or cheaper agent sessions. No token/cost savings claim is supported by this audit.

## Sequencing recommendation for Opus

Honor Derek's current G4b review boundary; do not use this audit to reopen accepted move polish. Complete source-art preservation from PLAN_CLEANUP first, with the safeguards in its Codex review. The roster extraction can follow as a small independent no-behavior-change task before new wrestlers are added; it need not block the current splash review. Keep broad docs moves separate. Finisher dispatch belongs to PLAN_FINISHERS F1.1, and story save ownership belongs to the next story task. Asset inventory can be read-only; selective preloading/resizing waits for measurements.
